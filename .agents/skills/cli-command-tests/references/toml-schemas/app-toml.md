# `shopify.app.toml` schema history

`shopify.app.toml` has never had a durable `schema_version` field. This history identifies the structures the CLI and official templates have accepted, so we can test old files and normalize them into one internal representation.

This is shared app-configuration knowledge. Apply it only to commands that read, generate, link, validate, or write these files. A schema's historical existence does not prove current acceptance or automatic migration.

The labels in this document (`T1`, `L1`, and so on) are research labels, not public Shopify version numbers. The history has two parallel tracks:

1. **Template files** are incomplete by design. Linking fills in the missing app details.
2. **Linked app files** describe an existing app. The CLI validates them against the app configuration schemas.

Migration code must keep those states separate. Treating a template as a complete linked-app configuration would reject files generated by Shopify's own templates.

## Notation

Schemas use TypeScript-like notation because it can express required and optional properties more precisely than a sample TOML file:

- `property: T` is required.
- `property?: T` is optional.
- `T[]` is an array.
- `A | B` is a union.
- `URL` is an HTTP(S) URL unless a wider URI type is stated.
- `WebhookURI` is an HTTPS URL, a relative path beginning with `/`, a Google Pub/Sub URI, or an Amazon EventBridge ARN. The CLI also accepts internal `kafka://` URIs.
- Unless stated otherwise, nested tables reject values of the wrong type. Historical strict schemas also rejected unknown keys.

Structural changes define the migration boundaries: `L1` → `L2`, `L3` → `L4`/`L5`, and template → linked configuration. Additive fields such as `filter` and `optional_scopes` do not identify a version on their own.

## Template formats

### T1: Minimal legacy template

**Introduced:** 2022-04-08 in [`shopify-app-template-node@0f306c1`](https://github.com/Shopify/shopify-app-template-node/commit/0f306c18949aab1a31cabe689c1bbd88ab895049).

The first file contained only `name`. [`f54522a`](https://github.com/Shopify/shopify-app-template-node/commit/f54522acc6e1ee77fcdbec96fd5352ae4cd7040a) added root `scopes` on 2022-04-20. The value changed from `read_products` to `write_products` the next day, and the template dropped `name` on 2022-05-25/26.

#### Full accepted schema

The legacy schema before webhook support was a superset of the earliest template files:

```ts
interface T1LegacyTemplate {
  // A numeric ID was accepted for very old generated files. It was not the
  // modern string client ID.
  client_id?: number
  name?: string
  scopes?: string // Zod default: ""
  extension_directories?: string[]
  web_directories?: string[]
}
```

#### Representative TOML

```toml
scopes = "write_products"
```

#### Change from the previous format

This was the first repository-owned app TOML format. The 2022 template history changed values and removed the optional display name, but did not introduce another structural schema.

#### Matching and migration

- Match before legacy support was removed: no linked-app-only keys and `client_id` absent or numeric.
- Migrate `scopes` to `access_scopes.scopes`.
- Do not invent linked-app values. `client_id`, `name`, `application_url`, `embedded`, and `auth.redirect_urls` must come from app creation/linking or an explicit defaulting policy.

[`f405481`](https://github.com/Shopify/cli/commit/f40548192a78f64bcb498d803a00f8b0e911671e) removed the strict legacy schema from the CLI on 2025-11-05. The React Router template added its string `client_id` placeholder one week later. All three templates moved to nested access scopes in February 2026.

### T2: Legacy template with declarative webhooks

**Introduced:** [`shopify-app-template-remix@7bcba98`](https://github.com/Shopify/shopify-app-template-remix/commit/7bcba988e61884b500c266bd26171b95d7683e73) added the format on 2024-06-12. [`5120aa6`](https://github.com/Shopify/shopify-app-template-remix/commit/5120aa6b533e75ca0b20958d19f570c4778fa1b1) switched to relative webhook paths on 2024-06-14. The CLI added support on 2024-06-13 in [`f5d0946`](https://github.com/Shopify/cli/commit/f5d09462c1783debd6fa8d69f79727120968a19c), released in CLI 3.63.0.

#### Full accepted schema

```ts
interface T2LegacyTemplateWithWebhooks {
  client_id?: number
  name?: string
  scopes?: string
  extension_directories?: string[]
  web_directories?: string[]
  webhooks?: {
    api_version: string
    subscriptions?: Array<{
      topics?: string[]
      uri: WebhookURI
      include_fields?: string[]
      filter?: string
      compliance_topics?: Array<
        "customers/redact" | "customers/data_request" | "shop/redact"
      >
    }>
  }
}
```

#### Representative TOML

```toml
scopes = "write_products"

[webhooks]
api_version = "2024-10"

[[webhooks.subscriptions]]
topics = ["app/uninstalled"]
uri = "/webhooks/app/uninstalled"

[[webhooks.subscriptions]]
topics = ["app/scopes_update"]
uri = "/webhooks/app/scopes_update"
```

#### Change from T1

- Added `[webhooks].api_version`.
- Added `[[webhooks.subscriptions]]` using the modern subscription shape.
- Kept `scopes` at the root, so this was still a template-only legacy format rather than a complete linked configuration.

Later Remix commits changed examples and API versions, not the schema. They added and then commented out compliance examples, removed `products/create`, documented `filter` in comments, and added `app/scopes_update`.

### T3: Hybrid React Router template

**Introduced:** 2025-11-12 in [`shopify-app-template-react-router@fcfa5b2`](https://github.com/Shopify/shopify-app-template-react-router/commit/fcfa5b27511f4e1522641522f2f5ae5d083a1f4e).

#### Full template shape

```ts
interface T3HybridTemplate {
  client_id: "" // Placeholder string, populated during linking.
  scopes: string // Still at the root.
  webhooks?: {
    api_version: string
    subscriptions?: ModernWebhookSubscription[]
  }
}
```

#### Representative TOML

```toml
client_id = ""
scopes = "write_products"

[webhooks]
api_version = "2025-10"

[[webhooks.subscriptions]]
topics = ["app/uninstalled"]
uri = "/webhooks/app/uninstalled"
```

#### Change from T2

This format added an empty string `client_id` placeholder. It is a transitional hybrid. The old strict legacy schema expected a numeric client ID, while the linked schema expected nested scopes and other app fields. The current template loader handles this file with a permissive schema instead of the linked-app validator.

Add this exact shape to the E2E fixtures. A matcher that checks only for a string `client_id` will mistake it for a linked app.

### T4: Current template seed

**Introduced:** 2026-02-04 in:

- [`shopify-app-template-remix@ca343bf`](https://github.com/Shopify/shopify-app-template-remix/commit/ca343bf028cfc7e50510d6118d26998782fde55e)
- [`shopify-app-template-react-router@950dc7d`](https://github.com/Shopify/shopify-app-template-react-router/commit/950dc7d9da017d4161e0cc70b86243622ee3caa2)

The Node template followed on 2026-02-05 in [`96edeb2`](https://github.com/Shopify/shopify-app-template-node/commit/96edeb2f7b11b59c220444063bd39e63d6ab92b3).

#### Full template shape

```ts
interface T4CurrentTemplate {
  client_id: "" // Placeholder string.
  access_scopes: {
    scopes: string
  }
  webhooks?: {
    api_version: string
    subscriptions?: ModernWebhookSubscription[]
  }
}
```

#### Representative TOML

```toml
client_id = ""

[access_scopes]
scopes = "write_products"

[webhooks]
api_version = "2025-10"

[[webhooks.subscriptions]]
topics = ["app/uninstalled"]
uri = "/webhooks/app/uninstalled"
```

#### Change from T3

This format moved root `scopes` to `[access_scopes].scopes`. Its field location matches the current linked-app schema, but the file stays incomplete until linking fills the empty client ID and other app modules.

## Linked app formats

### L1: First config-as-code prototype

**Introduced:** 2023-06-26 in [`Shopify/cli@8c0cdb1`](https://github.com/Shopify/cli/commit/8c0cdb162166265168e01ba65bf2286ced7c7c53). Shopify replaced it before the first Config as Code release. Treat it as a historical migration input, not a public contract.

#### Full schema

```ts
interface L1FlatConfigAsCode {
  name: string
  api_contact_email: string
  client_id: string
  scopes?: string
  webhook_api_version: string
  application_url: string
  embedded?: boolean
  legacy_scopes_behavior?: boolean // Added 2023-06-29.

  auth?: {
    redirect_urls: string[]
  }
  privacy_compliance_webhooks?: {
    customer_deletion_url: string
    customer_data_request_url: string
    shop_deletion_url: string
  }
  proxy?: {
    url: string
    subpath: string
    prefix: string
  }
  pos?: {
    embedded: boolean
  }
  app_preferences?: {
    url: string
  }
  cli?: {
    automatically_update_urls_on_dev?: boolean
    dev_store_url?: string
  }
  extension_directories?: string[]
  web_directories?: string[]
}
```

#### Change from T1

- Added a required string `client_id` and app metadata.
- Added app URL, embedding, auth, webhook API version, privacy URLs, proxy, POS, preferences, and CLI settings.
- Continued to store scopes at the root.

#### Upgrade to L2

```text
scopes                              -> access_scopes.scopes
legacy_scopes_behavior              -> access_scopes.use_legacy_install_flow
webhook_api_version                 -> webhooks.api_version
privacy_compliance_webhooks         -> webhooks.privacy_compliance
proxy                               -> app_proxy
cli                                 -> build
api_contact_email                   -> remove (moved out of TOML)
```

### L2: Released nested config-as-code schema

**Introduced:** 2023-07-07 in [`f4222bf`](https://github.com/Shopify/cli/commit/f4222bf6561e8ed477e367f755eec2e9d98f5746), released in CLI 3.48.0. The CLI tightened URL and type constraints on 2023-07-14. [`5398204`](https://github.com/Shopify/cli/commit/5398204ab52ac78950cb2d3ca3ab036bdfec8823) removed `api_contact_email` on 2023-07-18.

#### Full schema

```ts
interface L2NestedConfig {
  name: string // Maximum 30 characters.
  client_id: string
  application_url: URL
  embedded: boolean

  access_scopes?: {
    scopes?: string
    use_legacy_install_flow?: boolean
  }
  auth?: {
    redirect_urls: URL[]
  }
  webhooks: {
    api_version: string
    privacy_compliance?: {
      customer_deletion_url?: URL
      customer_data_request_url?: URL
      shop_deletion_url?: URL
    }
  }
  app_proxy?: {
    url: URL
    subpath: string
    prefix: string
  }
  pos?: {
    embedded: boolean
  }
  app_preferences?: {
    url: URL // Maximum 255 characters.
  }
  build?: {
    automatically_update_urls_on_dev?: boolean
    dev_store_url?: string
  }
  extension_directories?: string[]
  web_directories?: string[]
}
```

#### Change from L1

L2 applies the mappings above, requires `application_url` and `embedded`, nests webhook settings, and removes `api_contact_email`.

### L3: Declarative webhook prototype using `endpoint`

**Introduced:** 2023-11-01 in [`4fd0a47`](https://github.com/Shopify/cli/commit/4fd0a470bea1463172458369e8bf08e6f3ebf6f1), released in CLI 3.52.0. The singular endpoint design was completed on 2023-11-14 in [`14fb416`](https://github.com/Shopify/cli/commit/14fb4169a548c7c1acf68b3e36db8cce68b4c634).

#### Full schema

L3 has every L2 field, with this expanded `webhooks` table:

```ts
interface L3EndpointWebhooksConfig
  extends Omit<L2NestedConfig, "webhooks"> {
  webhooks: {
    api_version: string
    privacy_compliance?: {
      customer_deletion_url?: URL
      customer_data_request_url?: URL
      shop_deletion_url?: URL
    }

    // Shorthand for topics sharing one destination.
    topics?: [string, ...string[]]
    endpoint?: HTTPSUrl | PubSubURI | EventBridgeARN

    subscriptions?: Array<{
      topic: string
      endpoint?: HTTPSUrl | PubSubURI | EventBridgeARN
      path?: string // Starts with "/" and has length > 1.
      sub_topic?: string
      include_fields?: string[]
      metafield_namespaces?: string[]
    }>
  }
}
```

#### Change from L2

Added declarative webhook subscriptions in two forms:

1. A top-level `webhooks.topics` + `webhooks.endpoint` shorthand.
2. Per-subscription singular `topic`, optional `endpoint`, and optional `path`.

The transform expanded both forms into one remote subscription per topic. The field names require a rewrite before the modern `topics` + `uri` parser can read them, so L3 needs its own migration step.

An unmerged development branch briefly tried a `version = "3"` discriminator in [`5bf6bf0`](https://github.com/Shopify/cli/commit/5bf6bf0425cbf879d3f3d53e23da22a81b3c55fb), then removed it three days later in [`95a2a8c`](https://github.com/Shopify/cli/commit/95a2a8c2ae4e7e025bc7820250fd91093c48005f). It never reached the main CLI history or any of the three official templates. A migration can discard the field if found, but must not rely on it as a shipped version marker.

### L4: Modular schema and `uri`

**Introduced:** [`124f6cf`](https://github.com/Shopify/cli/commit/124f6cff72168ce66e9fcf3373aa3ddba159d3d6) added the module-composed loader on 2023-12-12. [`365f732`](https://github.com/Shopify/cli/commit/365f732820c493af5eb66887ebd58a0969ac63b4) renamed webhook `endpoint` to `uri` on 2023-12-22; the change shipped in CLI 3.53.0.

#### Full schema

```ts
interface L4UriWebhooksConfig
  extends Omit<L3EndpointWebhooksConfig, "webhooks"> {
  webhooks: {
    api_version: string
    privacy_compliance?: {
      customer_deletion_url?: WebhookURI
      customer_data_request_url?: WebhookURI
      shop_deletion_url?: WebhookURI
    }
    topics?: [string, ...string[]]
    uri?: HTTPSUrl | PubSubURI | EventBridgeARN
    subscriptions?: Array<{
      topic: string
      uri?: HTTPSUrl | PubSubURI | EventBridgeARN
      path?: string
      sub_topic?: string
      include_fields?: string[]
      metafield_namespaces?: string[]
    }>
  }
}
```

#### Change from L3

- Renamed every webhook `endpoint` property to `uri`.
- Did not include the development-only root `version` field.
- Replaced the monolithic schema with a base schema merged with app-module schemas. This internal change did not alter TOML syntax.

#### Upgrade to L5

```text
webhooks.endpoint                         -> each subscription.uri
webhooks.topics                           -> each subscription.topics
webhooks.subscriptions[].endpoint         -> webhooks.subscriptions[].uri
webhooks.subscriptions[].topic            -> webhooks.subscriptions[].topics = [topic]
webhooks.subscriptions[].path + base URI  -> webhooks.subscriptions[].uri
```

### L5: Modern subscription array baseline

**Introduced:** [`cf3acc3`](https://github.com/Shopify/cli/commit/cf3acc3bc4f95e008c6fd5dfe79558208a29dd32) added the modern webhook array on 2024-01-10. The L5 snapshot spans 2024-01-09 through 2024-01-17 because the surrounding commits added the build deployment switch, direct API settings, and the final `handle` spelling.

#### Full schema

```ts
interface L5ModernSubscriptions {
  name: string // Maximum 30 characters.
  handle?: string // URL-safe slug; maximum 256 characters.
  client_id: string
  application_url: URL
  embedded: boolean
  extension_directories?: string[]
  web_directories?: string[]

  access?: {
    admin?: {
      direct_api_mode?: "online" | "offline"
      embedded_app_direct_api_access?: boolean
    }
  }
  access_scopes?: {
    scopes?: string
    use_legacy_install_flow?: boolean
  }
  auth?: {
    redirect_urls: URL[]
  }
  webhooks: {
    api_version: string
    privacy_compliance?: {
      customer_deletion_url?: WebhookURI
      customer_data_request_url?: WebhookURI
      shop_deletion_url?: WebhookURI
    }
    subscriptions?: Array<{
      topics: [string, ...string[]]
      uri: HTTPSUrl | PubSubURI | EventBridgeARN
      sub_topic?: string
      include_fields?: string[]
      metafield_namespaces?: string[]
      compliance_topics?: Array<
        "customers/redact" | "customers/data_request" | "shop/redact"
      >
    }>
  }
  app_proxy?: {
    url: URL
    subpath: string
    prefix: string
  }
  pos?: {
    embedded: boolean
  }
  app_preferences?: {
    url: URL
  }
  build?: {
    automatically_update_urls_on_dev?: boolean
    dev_store_url?: string
    include_config_on_deploy?: boolean
  }
}
```

#### Change from L4

- Removed webhook-level `topics` and `uri` shorthand.
- Changed subscription `topic` to `topics: string[]`.
- Made subscription `uri` the complete destination; `path` was no longer needed.
- Added `handle` (first called `app_handle`, renamed by [`302bd59`](https://github.com/Shopify/cli/commit/302bd59c43aa773d3ddbe7862bb213f6493f8d8a)).
- Added `[access.admin]` with `direct_api_mode` and `embedded_app_direct_api_access` in [`434604d`](https://github.com/Shopify/cli/commit/434604ddb0f3062ad1116b8a5d0d16e120aa7505).
- Added `build.include_config_on_deploy` in [`f79606b`](https://github.com/Shopify/cli/commit/f79606b1f17872d3fba5a1402b100cba1dc182fd).

`[auth]` became required on 2024-01-25 in [`4417262`](https://github.com/Shopify/cli/commit/4417262951c67009abda67035cdee6feb3f379ee) and remains required in L6.

[`327c30d`](https://github.com/Shopify/cli/commit/327c30d22d0708fd656d382652e7635d36456826) briefly removed declarative subscriptions on 2024-01-25. They returned with the consolidated compliance format on 2024-02-06. This feature-gating interval did not create a persistent file syntax, but an E2E suite for historical CLI releases should record it.

### L6: Consolidated modern schema

**Introduced:** 2024-02-06 in [`1035bf1`](https://github.com/Shopify/cli/commit/1035bf1d2271fc68da52bbd7209b86f562cbc924).

#### Full schema at introduction

```ts
interface L6ConsolidatedConfig {
  name: string
  handle?: string
  client_id: string
  application_url: URL
  embedded: boolean
  extension_directories?: string[]
  web_directories?: string[]

  access?: {
    admin?: {
      direct_api_mode?: "online" | "offline"
      embedded_app_direct_api_access?: boolean
    }
  }
  access_scopes?: {
    scopes?: string
    use_legacy_install_flow?: boolean
  }
  auth: {
    redirect_urls: URL[]
  }
  webhooks: {
    api_version: string
    privacy_compliance?: {
      customer_deletion_url?: WebhookURI
      customer_data_request_url?: WebhookURI
      shop_deletion_url?: WebhookURI
    }
    subscriptions?: Array<{
      // `topics` became optional on 2024-03-20 so a compliance-only
      // subscription could be represented.
      topics?: string[]
      uri: WebhookURI
      sub_topic?: string
      include_fields?: string[]
      metafield_namespaces?: string[]
      compliance_topics?: Array<
        "customers/redact" | "customers/data_request" | "shop/redact"
      >
    }>
  }
  app_proxy?: {
    url: URL
    subpath: string
    prefix: string
  }
  pos?: {
    embedded: boolean
  }
  app_preferences?: {
    url: URL
  }
  build?: {
    automatically_update_urls_on_dev?: boolean
    dev_store_url?: string
    include_config_on_deploy?: boolean
  }
}
```

#### Change from L5

`compliance_topics` puts privacy subscriptions in the same array as ordinary subscriptions. The CLI still accepts `webhooks.privacy_compliance` and transforms both forms to the same remote module. A file cannot use both forms at once.

#### Revisions within L6

These fields do not identify separate top-level versions, but the fixtures still need to cover them:

| Date       | Commit                                                                                      | Schema change                                                                                                                                           |

### L7: Current canonical schema

**Introduced:** incrementally. The current shape combines the public reference with the fields that the CLI still accepts for compatibility.

The schema marks three kinds of fields:

- **Public** fields appear in the current app configuration reference.
- **Compatibility** fields remain explicitly understood by current CLI code but are no longer in the public reference.
- **Platform/dynamic** fields come from remotely described app modules and might not have a dedicated static Zod object in this repository.

#### Full schema

```ts
interface L7CanonicalAppConfiguration {
  // Public global fields
  name: string
  handle?: string
  client_id: string
  application_url: URL
  embedded: boolean
  extension_directories?: string[]
  web_directories?: string[]

  access?: {
    admin?: {
      direct_api_mode?: "online" | "offline"
      embedded_app_direct_api_access?: boolean
    }
  }

  access_scopes: {
    // Public canonical representation.
    scopes: string
    optional_scopes?: string[]
    use_legacy_install_flow?: boolean

    // CLI compatibility representation; not in the current public page.
    required_scopes?: string[]
  }

  auth: {
    redirect_urls: URL[]
  }

  // Public, platform/dynamic module.
  customer_authentication?: {
    redirect_uris: URL[]
    javascript_origins?: URL[]
    logout_urls?: URL[]
  }

  webhooks: {
    api_version: string

    // CLI compatibility representation; public docs use compliance_topics.
    privacy_compliance?: {
      customer_deletion_url?: WebhookURI
      customer_data_request_url?: WebhookURI
      shop_deletion_url?: WebhookURI
    }

    subscriptions?: ModernWebhookSubscription[]
  }

  // Public, platform/dynamic module.
  events?: {
    api_version: string
    subscription?: Array<{
      handle: string
      topic: string
      actions: Array<"create" | "update" | "delete">
      uri: WebhookURI
      triggers?: string[]
      query?: string
      query_filter?: string
    }>
  }

  app_proxy?: {
    url: URL
    subpath: string
    prefix: "a" | "apps" | "community" | "tools"
  }
  pos?: {
    embedded: boolean
  }
  app_preferences?: {
    url: URL
  }
  build?: {
    automatically_update_urls_on_dev?: boolean
    dev_store_url?: string

    // CLI compatibility field; deprecated and absent from current docs.
    include_config_on_deploy?: boolean
  }
}

interface ModernWebhookSubscription {
  // Public docs describe topics as required, while the CLI permits a
  // compliance-only subscription with no topics.
  topics?: string[]
  compliance_topics?: Array<
    "customers/redact" | "customers/data_request" | "shop/redact"
  >
  uri: WebhookURI
  filter?: string
  include_fields?: string[]

  // Explicitly accepted by current CLI, but absent from the current public page.
  actions?: string[]
  payload_query?: string
  name?: string // Trimmed, 1–50 characters.
}
```

#### Current validation rules

- A webhook subscription must contain at least one of `topics` or `compliance_topics`.
- A compliance topic can occur only once across the file.
- `webhooks.privacy_compliance` and subscription-level `compliance_topics` cannot be mixed.
- Duplicate ordinary webhook subscriptions are keyed by `topic`, `uri`, and `filter`.
- Relative webhook and event URIs are resolved against `application_url` for remote configuration.
- `name` is limited to 30 characters by the CLI's branding module.
- `handle` is optional, limited to 256 characters, and validated as a URL-safe app handle.
- `app_proxy` constraints are stricter on the platform than in the local Zod schema: public docs restrict `prefix` and constrain `subpath`.

#### Change from L6

- Added current webhook fields `payload_query`, `actions`, and `name`.
- Added `[customer_authentication]` in the public/platform schema.
- Added `[events]` and `[[events.subscription]]`; the CLI added its local transform in February 2026.
- Removed `organization_id` from the supported local contract.
- Deprecated `build.include_config_on_deploy`, because app configuration is always included for App Management apps.
- Kept compatibility readers for `required_scopes` and `webhooks.privacy_compliance` even though the public documentation presents `scopes` and `compliance_topics` as canonical.

## Source discrepancies

### Templates versus linked schemas

Templates are seeds, not examples of the complete public schema. They kept root `scopes` until February 2026, even though linked apps had used `[access_scopes]` since July 2023. The Remix template also paired modern declarative webhooks with the otherwise legacy template schema.

### CLI versus current public docs

| Topic                     | Current public docs                         | Current CLI behavior                                                                                                            |
| ------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Required scopes           | `access_scopes.scopes: string` is required. | Also understands `required_scopes: string[]`; `scopes` remains optional in static Zod because legacy install flow is supported. |
| Old privacy webhooks      | Not documented.                             | `webhooks.privacy_compliance` is still accepted and transformed.                                                                |
| Webhook-only subscription | `topics` is described as required.          | `topics` may be absent when `compliance_topics` is present.                                                                     |
| Extra webhook fields      | Documents `filter` and `include_fields`.    | Also accepts `actions`, `payload_query`, and `name`.                                                                            |
| Build deployment switch   | Not documented.                             | `include_config_on_deploy` is parsed for compatibility and removed in modern App Management flows.                              |
| Customer authentication   | Documented.                                 | Supplied by a dynamic platform specification rather than a dedicated static schema in this checkout.                            |
| Events                    | Documented.                                 | The local wrapper intentionally uses `z.any()` and relies on the platform contract for detailed validation.                     |
| App proxy URL             | Documented as an absolute URL.              | The local transform also accepts a relative path and resolves it against `application_url`.                                     |
| Webhook URI               | HTTPS, relative, Pub/Sub, or EventBridge.   | Also accepts internal `kafka://` destinations.                                                                                  |

No source is complete on its own. The effective schema combines the base CLI schema, platform-provided app-module contracts, and local compatibility fields.

## Recommended migration chain

**Design proposal, not implemented command behavior.** The steps below describe a possible versioned normalization system. Tests of today's CLI must assert its actual acceptance, rejection, or field loss instead of assuming these migrations run.

Use ordered structural matchers. Optional fields are poor version signals:

1. **`T3` hybrid template:** `client_id === ""`, root `scopes` present, no `access_scopes`.
2. **`T4` current template:** `client_id === ""`, `access_scopes.scopes` present, and required linked fields absent.
3. **`T1`/`T2` legacy template:** root `scopes` present and no non-empty string `client_id`.
4. **`L1` flat config-as-code:** any of `webhook_api_version`, `privacy_compliance_webhooks`, `proxy`, `cli`, or `legacy_scopes_behavior` exists.
5. **`L3` endpoint webhooks:** `webhooks.endpoint` or `webhooks.subscriptions[].endpoint` or singular subscription `topic`/`path` exists.
6. **`L4` URI shorthand:** `webhooks.topics` or `webhooks.uri` exists at the webhook-table level.
7. **`L5` old modern subscriptions:** `sub_topic` or `metafield_namespaces` exists, or old `webhooks.privacy_compliance` exists.
8. **`L6` compatibility schema:** modern structure with compatibility-only fields such as `required_scopes` or `include_config_on_deploy`.
9. **`L7` canonical schema:** current public structure.

Keep every `up` function pure, and preserve unknown and dynamic app-module tables. The core CLI must not discard custom-data definitions or remotely supplied modules it does not know statically.

Suggested transformations:

```text
T1/T2/T3 -> linked input
  scopes -> access_scopes.scopes
  preserve webhooks
  obtain missing linked-app values outside the pure transform

L1 -> L2
  apply the field mappings in the L1 section

L3 -> L4
  endpoint -> uri
  join a subscription path to its inherited base URI

L4 -> L5
  expand top-level topics into a subscription
  topic -> topics = [topic]

L5 -> L6
  privacy_compliance URLs -> compliance_topics subscriptions
  remove sub_topic only with an explicit product decision; it has no lossless
  canonical equivalent unless it can be translated to filter

L6 -> L7
  scopes/required_scopes -> choose one canonical internal scope array
  remove deprecated CLI-only fields from the core representation
  preserve module-specific fields in typed module payloads
```
